# 主题列车改乘时从旅行留言恢复同行约定

主题列车改乘工作簿记录旅客和来信、替代车次、体验券及票务余位变化。所有人名、编号和业务记录都是合成数据。

使用 Python 3.11 和标准库，资料文件采用 UTF-8。业务资料的格式记录在 [资料说明](资料说明.md)。

运行资料检查会读入记录、核对字段并显示各集合的条数。也可在后面指定单独的集合名。

```sh
python3 read_materials.py
python3 -m unittest discover -s tests -v
```

## 值班台

`rebook.py` 在同一份合成资料上恢复约定、列方案并办理改乘。

```sh
python3 rebook.py status                       # 通告范围、已确认条件、待答问题
python3 rebook.py plans --limit 3              # 候选整套方案
python3 rebook.py confirm <方案> \
    --actor p1 --actor p3 --actor p5 --request B90
python3 rebook.py lookup B90                   # 按回复号查办理结果
```

## 规则落点

- **通告范围**：只使用 `accepted` 且被通告点为可改/备用的班次。备用班次按原
  上车站搭乘；临时补进的站只对改乘班次开放。
- **人**：昵称和代词先展开成候选，再按同一分句的车站线索与同一封信的上下文
  消歧。两位同名“陈师傅”靠订单与自报车站区分，绝不按姓名合并。同一人可持
  多张订单，账户联系人只代表变更权限，不等于乘车人。
- **确认权限**：本人，或订单上登记的账户联系人，才能确认变更。字面上的转述
  只记为 `relayed`；“等我选车可以、替我答复不行”会把账户联系人的代确认权限
  收回，只留下代选权。
- **提议与回答**：`可不等`、`可以先走` 先记为提议并生成具体问题；只有被提议
  的人本人回答“也成”等才转为已接受。未回答的提议不进入任何硬约束。
- **收回与冲突**：持券人后来“先别转”优先于此前的附条件转让。冲突处理保留已
  确认的局部条件（座位、下车站、上车站），并给出能解除阻塞的问题。
- **体验券**：必须同时满足券的 `feature`、`required_stop` 与实际乘坐区间；转让
  另需仍然有效的授权，受让人还须落在 `recipient_scope`。无法兑现时把取舍与
  问题交给旅客，绝不先替别人核销。
- **方案与确认**：同行同车、本人可接受上车站、券规则和余位都是硬约束；座位与
  换站数只用于排序。一次确认绑定当时展示的整套方案（含条件指纹）。确认前若
  转让被收回、余位被其他订单占用或会话条件变化，原方案失效，重核会说明哪些
  条件变了并给出可重发的新方案。
- **一致查询**：同一回复号成功办理后反复查询返回同一份结果；同一回复号不能
  改办另一套方案，已办理的订单也不能重复确认。

## 模块

- `rebooking/model.py`：读取与校验六份资料，建立 person 与订单索引。
- `rebooking/entities.py`：昵称、姓氏称呼、代词的候选与车站限定消歧。
- `rebooking/conversation.py`：把往来读成 `confirmed`/`relayed`/`proposed`/
  `unresolved` 等可追溯表态，落账同行、上车站、券转让与待答问题。
- `rebooking/desk.py`：读通告、生成方案、复核指纹与办理确认。

## 已知取舍

- 会话语句用关键词加车站线索解析，不是通用自然语言理解。它针对本合成资料
  中出现的句式（同车、只走/只到、也成、可不等、券给/别转、替我答复等），新
  句式应先补测试再扩规则。
- 未受影响的订单不会因为同行约束被主动改票；同行约束只对真正需要改乘的订单
  生效。若业务要求整组一起改，需要额外的“全员重排”开关。
